# Чат із менеджером: сайт uagreen.co → Господар

Дата: 2026-11-23. Статус: на затвердженні.

## Навіщо

На старому сайті (Weblium) стоїть BinotelChat, і менеджер відповідає в окремому
вікні Binotel. Новий сайт (цей репозиторій) чату не має. Мета: відвідувач пише
менеджеру просто на сайті, а менеджер бачить і відповідає в Господарі
(erp.uagreen.co), де вже живуть клієнти, угоди, дзвінки й сповіщення.

Розмова — це ще не лід. **Менеджер сам створює ліда, коли розмова йде успішно.**

Друга мета — з'ясувати, яке вступне питання краще заводить відвідувача в розмову:
чат сам пропонує одне із заготовлених питань, а Господар рахує, яке спрацювало.

## Цілі

1. Віджет чату на кожній сторінці сайту (uk і en).
2. Відвідувач пише одразу, без імені й телефону. Телефон — необов'язкове поле,
   яке з'являється після першого повідомлення.
3. Розмова прив'язана до браузера: повернувся пізніше — бачить історію й відповіді.
4. У Господарі: розділ «Чати» в CRM — спільна скринька продажників, відповідь,
   кнопка «Створити ліда».
5. Після «Створити ліда» переписка видна в картці угоди на вкладці «Чати»
   (вона вже є і порожня), і відповідати можна звідти.
6. Сповіщення менеджерам про нові повідомлення: у застосунку і в Telegram.
7. Проактивне питання: через 30 с над кнопкою чату з'являється картка з одним
   питанням зі списку. Список і статистика (показано / відповіли / ліди) — у Господарі.

## Не робимо (перша версія)

- Файли й фото в чаті.
- Автовідповіді в неробочий час.
- Viber / Telegram / Instagram в одній скриньці з чатом.
- Сповіщення відвідувачу про відповідь на пошту чи SMS.
- Добір питання під конкретну сторінку (питання 11 — лише в магазині тощо).
- Індикатор «менеджер друкує», позначки «прочитано» для відвідувача.
- Передача розмови іншому менеджеру окремою кнопкою (відповісти може будь-хто з продажників).

## Антицілі (провал, навіть якщо «працює»)

- Господар відкритий для анонімного інтернету: боти й спам ідуть прямо в ERP.
- Чат гальмує сайт: важчає перше завантаження сторінки, ламається SSR.
- Картка-питання дратує: перекриває сторінку, вискакує щоразу, з'являється в кошику
  чи на оформленні замовлення.
- Спам засипає Telegram продажників.
- Сайт ламається, коли Господар недоступний.

## Як працює зараз (що використовуємо)

**Господар** (`D:/Work/Gospodar`, .NET 9 + Flutter web, мультикомпанійний):
- Інтеграційний вхід за ключем компанії: `ApiKeyAuthenticationHandler`
  (`X-Api-Key`, `companies.integration_key_hash`, claim `company`), політика
  `ServicePolicies.IntegrationCompany`. Так працює `POST /api/integration/leads`
  (заявки Оберегу → `CreateIntegrationLeadCommand`).
- Ліди: `CreateDealCommand`; джерело угоди заводиться на льоту (`SourceIdAsync`
  у `CreateIntegrationLeadHandler`); продажники — `SalesManagers.UserIds`
  (посада «Менеджер з продажу»), запасний варіант — власники `crm.manage_deals`.
- Сповіщення: `INotificationService.SendToUserAsync` (SignalR `/hubs/notifications`
  + історія в `user_notifications`) і `IExternalNotificationDispatcher.DispatchToUserAsync`
  (Telegram / web push / пошта за налаштуваннями користувача). Зразок —
  `PaymentClaimCommands`.
- Картка угоди: стрічка `DealTimelineHandler` (`note` / `call` / `stage`), у Flutter
  `DealEventKind.chat` і вкладка «Чати» вже є (`deal_side_rail.dart`, `_History`),
  поле вводу — `NoteComposer`.
- CRM-сторінки — `CrmPage` у `crm_screen.dart` (`/crm`, `/crm/tasks`, …).
- Права CRM: `crm.view`, `crm.manage_deals`, `crm.manage_settings`, …

**Сайт** (цей репозиторій):
- Nuxt 3 (`frontend/`), i18n uk (без префікса) / en (`/en/`), Tailwind, `layouts/default.vue`.
  Браузер ходить у `/api/*` того ж домену (nginx → API).
- .NET minimal API (`backend/src/UaGreen.Site.Api`): публічні форми з пасткою для
  ботів (`website`) і обмеженням частоти (`RateLimitingExtensions.Forms`),
  `Notifier` (лист менеджерам), `GospodarClient` (логін адмінки через Господар).
- Форма контактів `/api/contact` пише в базу сайту й шле лист — це запасний шлях,
  коли Господар недоступний.

## Дизайн

### Потік

```
Відвідувач ──► API сайту ──(ключ)──► Господар ──► продажники
   ▲  опитування 3 с │                   │        (SignalR + Telegram)
   └─────────────────┘◄──────────────────┘
```

API сайту — тонкий проксі: перевіряє ввід, тримає ліміти й пастку для ботів,
передає в Господар, нічого про чат у своїй базі не зберігає. Усі розмови,
повідомлення, питання й лічильники — у базі Господаря.

### Дані в Господарі (нові таблиці, з `company_id` як решта)

- **Розмова** (`chat_conversations`): номер гостя (послідовний у межах компанії,
  для «Гість #12»), хеш токена відвідувача, мова (uk/en), сторінка, з якої почав,
  ім'я й телефон (необов'язкові, з віджета), стартове питання (null, якщо
  відвідувач написав сам), хто веде (null, доки ніхто не відповів), поточна угода
  і клієнт (null, доки не прив'язали), стан (відкрита / закрита), час останнього
  повідомлення, хто написав останнім (відвідувач / менеджер).
- **Повідомлення** (`chat_messages`): розмова, автор (відвідувач або користувач
  Господаря), текст (до 2000 символів, звичайний текст), час, угода (проставляється
  при прив'язці — див. «Прив'язка до угоди»).
- **Питання** (`chat_questions`): текст uk, текст en (необов'язковий), активне,
  порядок, лічильник показів.

«Відповіли» = розмови з цим стартовим питанням. «Ліди» = ті з них, де хоч одне
повідомлення має угоду (розмова хоч раз ставала лідом).
Лічильник показів — одне число на питання (без розбивки за датами).

Стартові 11 питань (uk; en-переклад пише виконавець):
1. Бажаєте замовити аудит на своїй ділянці?
2. Маєте питання по наших станціях?
3. Чи потрібна вам консультація по наших послугах?
4. Хочете дізнатися, чи достатньо вітру на вашій ділянці?
5. Порахувати, за скільки окупиться вітрова станція саме у вашому випадку?
6. Шукаєте спосіб не залежати від відключень світла?
7. Підказати, яка станція вам підійде — на 1 кВт чи на 5 кВт?
8. Станцію шукаєте для дому чи для бізнесу?
9. Потрібні окремо лопаті, генератор чи щогла? Допоможемо підібрати сумісні.
10. Розповісти, як проходить встановлення — від огляду ділянки до запуску?
11. Є питання щодо доставки чи оплати?

### Ідентичність відвідувача

Перше повідомлення створює розмову; Господар генерує випадковий токен (≥128 біт),
зберігає лише його хеш і повертає токен. Віджет кладе токен і id розмови в
`localStorage`. Кожен наступний запит відвідувача несе токен; без нього розмову не
прочитати. Новий браузер / очищене сховище = нова розмова (це прийнятно).

### Вхід сайту в Господар

Окремий інтеграційний доступ для чату, прив'язаний до компанії UA Green.
**Обмеження:** ключ компанії зараз один (`companies.integration_key_hash`) і, ймовірно,
уже в Оберега; часті запити чату оновлювали б `IntegrationLastSeenAt` і ховали б
мовчання Оберега від `/health/integrations`. Тому чат не повинен ділити ключ з
Оберегом і не повинен зсувати його «востаннє бачили». Конкретний механізм — на
розсуд виконавця (наприклад, окремий ключ із конфігурації Господаря + id компанії).
Ключ живе лише в env бекенду сайту, у браузер не потрапляє.

### Віджет на сайті

- Кнопка в правому нижньому куті на всіх сторінках; код віджета вантажиться лише
  в браузері й не важчає SSR-сторінкою (лінива гідратація / client-only).
- Відкрите вікно: привітання, історія, поле вводу. Після першого повідомлення —
  необов'язкове «Залиште телефон — передзвонимо» (ім'я + телефон), яке потрапляє
  в розмову.
- Відповіді менеджера підписані його ім'ям (лише ім'я, без прізвища).
- Опитування: кожні 3 с, коли вікно відкрите; кожні 30 с, коли закрите, але
  розмова існує (щоб показати значок непрочитаного); пауза, коли вкладка прихована.
- Господар недоступний (API сайту відповідає 503): віджет показує форму «залиште
  телефон», яка йде через наявний `/api/contact`.
- Тексти віджета — у `i18n/locales/uk.json` і `en.json`. Повідомлення — лише
  звичайний текст з обох боків (без HTML).

### Картка-питання

- Через 30 с перебування на сайті (сумарно між сторінками в межах вкладки — на
  розсуд виконавця) над кнопкою з'являється картка «UA Green: <питання>» з полем
  відповіді. Чат повністю не розгортається.
- Питання — випадкове з активних; обране запам'ятовується в `localStorage`, і той
  самий відвідувач бачить те саме питання. Якщо його вимкнули — береться інше.
- Показ рахується (лічильник у Господарі) один раз на показ картки.
- Не показується: якщо в браузері вже є розмова; у кошику, на оформленні й на
  сторінці замовлення; 7 днів після того, як відвідувач закрив картку.
- На `/en/` — англійський текст; немає перекладу → картка на en-сторінках не показується.
- Відповідь на картку створює розмову, де першим повідомленням стоїть питання від
  «UA Green», а стартове питання записане в розмову.

### Скринька в Господарі: `/crm/chats`

- Новий пункт `CrmPage.chats` у меню «Комерція». Видно тим, хто має `crm.manage_deals`.
- Ліворуч список: спершу ті, що чекають відповіді (останнім написав відвідувач),
  далі за часом останнього повідомлення; ім'я / «Гість #N», уривок, хто веде.
  Фільтр «Закриті».
- Праворуч: переписка, сторінка, з якої почав, мова, контакти з віджета, стартове
  питання; поле відповіді; кнопки «Створити ліда» і «Закрити».
- Хто перший відповів — той веде (записується в розмову). Відповідати можуть усі
  продажники й далі.
- «Закрити» ховає розмову зі списку; нове повідомлення відвідувача відкриває її знову.
- Нові повідомлення в скриньці з'являються наживо через SignalR-подію.
- **Створити ліда**: наявна форма угоди, заповнена ім'ям і телефоном із чату,
  відповідальний — поточний менеджер, джерело «Чат на сайті» (заводиться на льоту,
  як «Оберіг»), у нотатку — сторінка, з якої почав, і стартове питання. Після
  створення розмова прив'язується до угоди й клієнта.
- **Прив'язати до угоди** (*рішення виконавця брейнштормінгу, не користувача*):
  друга кнопка поруч — вибір відкритої угоди. Якщо телефон/пошта з віджета
  збігаються з клієнтом, першими пропонуються його відкриті угоди. Так знайомий
  клієнт не отримує дубль угоди.

### Прив'язка до угоди (*рішення виконавця брейнштормінгу, не користувача*)

- При прив'язці (створення ліда або вибір наявної угоди) розмова отримує поточну
  угоду, а всі її повідомлення без угоди отримують цю угоду — переписка, що
  привела до ліда, видна в картці.
- Нові повідомлення, поки угода відкрита, одразу отримують її.
- Відвідувач пише знову, а поточна угода вже закрита (виграна / програна /
  видалена): прив'язка розмови знімається, нові повідомлення йдуть без угоди,
  у скриньці знову доступні «Створити ліда» і «Прив'язати до угоди». Стара угода
  зберігає свої повідомлення.

### Картка угоди

- `DealTimelineHandler` додає записи `chat` з повідомлень, у яких стоїть ця угода
  (автор — менеджер або «Клієнт»), вкладка «Чати» починає їх показувати.
- На вкладці «Чати» поле вводу надсилає повідомлення відвідувачу (а не нотатку),
  якщо до угоди прив'язана розмова. Кілька розмов на одній угоді (клієнт писав з
  двох браузерів) — відповідь іде в ту, де останнє повідомлення.

### Сповіщення

- Нове повідомлення відвідувача: якщо розмову ще ніхто не веде — усім продажникам
  (`SalesManagers.UserIds`, запасний варіант — власники `crm.manage_deals`);
  якщо веде — лише йому.
- Канали: `INotificationService.SendToUserAsync` + `IExternalNotificationDispatcher`.
  Посилання — на `/crm/chats?c=<id>`.
- Проти спаму в Telegram: не більше одного зовнішнього сповіщення на розмову, доки
  менеджер не відповів (наступні повідомлення відвідувача — лише в застосунку).

### Питання і статистика: `/crm/chats/questions`

- Таблиця: текст, вкл/викл, показано, відповіли (і % від показів), ліди.
- Додати, редагувати тексти uk/en, вмикати/вимикати. Видаляти не можна (статистика
  посилається), лише вимикати. Право — `crm.manage_settings`.
- Стартові 11 питань засіваються міграцією для компанії UA Green.

### Захист від зловживань

- API сайту: пастка для ботів на першому повідомленні; окрема політика частоти
  для чату (нові розмови — кілька на годину з IP, повідомлення — кілька на хвилину,
  опитування — досить, щоб вистачило 3-секундного інтервалу); точні числа — на
  розсуд виконавця, через `RateLimiting:Chat:*` у конфігурації, як решта.
- Господар перевіряє довжину тексту, токен відвідувача й належність розмови компанії.

### Поставка

- Два репозиторії, дві гілки: Господар — окрема гілка/worktree у `D:/Work/Gospodar`
  (основна копія має незакомічені зміни), сайт — ця гілка.
- Порядок викатки: спершу Господар (API + UI), потім сайт із ключем у env.
- Вимикач (*рішення виконавця брейнштормінгу*): без ключа чату в env сайту віджет
  і картка-питання не показуються взагалі. Новий сайт зараз живе лише на staging
  (new.uagreen.co), а Господар один — бойовий. Тому staging лишається без ключа,
  доки користувач не вирішить інакше: інакше тестові чати слатимуть Telegram
  справжнім продажникам і псуватимуть лічильники питань. Наскрізна перевірка —
  локально (сайт + Господар на машині розробника).
- Тести: бекенд Господаря — інтеграційні тести ендпоінтів (як `BinotelWebhookTests`);
  сайт — vitest для логіки картки-питання (вибір, «липкість», 7 днів, сторінки-винятки).

## Що лишається на розсуд виконавця

- Точний механізм окремого інтеграційного ключа для чату (з обмеженням вище).
- Форми URL ендпоінтів і DTO в обох API.
- Як рахувати 30 с (одна сторінка чи сумарно за вкладку).
- Числа лімітів частоти.
- Візуал віджета в межах стилю сайту; візуал скриньки в межах UI-kit Господаря.

## Поправка 2026-11-23: канал у наявній скриньці

Під час виконання з'ясувалося: у свіжому `main` Господаря вже є скринька «Чати»
(`/crm/chats`) для Telegram, Viber, WhatsApp і Facebook Messenger — з призначенням,
непрочитаними, швидкими відповідями, прив'язкою до картки клієнта і кнопками
«Створити ліда» / «Створити угоду». Користувач вирішив: **чат сайту — ще один канал
цієї скриньки**. Ця поправка має перевагу над розділами вище.

- **Дані.** Розмови й повідомлення — наявні `ChatConversation` / `ChatMessage` з
  каналом `Website = 5`; додаються лише `StartPageUrl` і `StarterQuestionId`. Нова
  таблиця — лише питання (`SiteChatQuestion`). Ідентифікатор відвідувача в розмові —
  хеш його токена (`ExternalChatId`).
- **Скринька, призначення, ліди.** Наявні: хто перший відповів — той веде; «Створити
  ліда» й прив'язка до картки клієнта; угоди клієнта видно поруч із чатом. Телефон із
  віджета сам знаходить картку клієнта. Окремої сторінки `/crm/chats` під сайт,
  прив'язки розмови до конкретної угоди і вкладки «Чати» в картці угоди **не робимо**
  (вкладка в картці угоди — окреме покращення для всіх каналів).
- **Сповіщення.** Наявний дзвіночок `chat_message_received` (призначеному або всім з
  `crm.chat`); для каналу «Сайт» додатково Telegram/web push тим самим людям — раз на
  «нову пачку непрочитаних» (до того, як менеджер прочитав або відповів).
- **Права.** Скринька — `crm.chat` (а не `crm.manage_deals`); питання — `crm.manage_settings`.
- **Питання і статистика** — вкладка «Сайт» у наявному діалозі налаштувань чатів.
  «Ліди» = розмови з питанням, чия картка клієнта має угоду, створену після початку розмови.
- **Для каналу «Сайт» недоступні**: файли, стікери, реакції, пересилання, редагування.
- **Без змін:** контракт API для сайту, ключ, вимикач, віджет, картка-питання, ліміти.
