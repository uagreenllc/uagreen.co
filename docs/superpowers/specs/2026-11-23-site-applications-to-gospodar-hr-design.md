# Відгуки на вакансії з сайту → HR Огляд Господаря

## Навіщо

HR працює в Господарі (erp.uagreen.co → Персонал → Найм → Кандидати). Відгук із форми
на сайті зараз лягає в базу сайту й показується в адмінці «Відгуки на вакансії», куди HR
не дивиться. Треба, щоб відгук одразу з'являвся карткою кандидата в колонці «Новий»
у Господарі, з резюме, на потрібній вакансії.

## Цілі / не-цілі / анти-цілі

- **Ціль:** кожен відгук із сайту (зокрема з загальної форми «не знайшли вакансію») стає
  кандидатом у Господарі, стадія «Новий», джерело «Сайт uagreen.co», резюме у вкладеннях.
- **Ціль:** HR сам прив'язує вакансію сайту до вакансії Господаря в адмінці сайту (список).
- **Не-ціль:** синхронізація самих вакансій (тексти, статуси) між системами. Список
  вакансій сайту вирівняно вручну 2026-11-23 (6 відкритих у Господарі = 6 активних на сайті).
- **Не-ціль:** сповіщення HR у Господарі (дзвіночок) — HR бачить колонку «Новий».
- **Анти-ціль:** відгук губиться, коли Господар недоступний або відповів помилкою.
- **Анти-ціль:** повтор відправки створює дубль кандидата.

## Обмеження (з коду)

- Господар: `Candidate.VacancyId` обов'язковий (`Vacancy` → обов'язкова `Specialty`).
  Кандидати й вакансії прив'язані до компанії (`BaseEntity.CompanyId`).
- Господар відхиляє нового кандидата з телефоном/email, що вже є серед кандидатів
  (`CandidateContacts.FindDuplicateError`).
- Ключ інтеграції сайту — ключ компанії (`X-Api-Key`, політика `IntegrationCompany`),
  той самий, яким сайт уже шле ліди в CRM (`CrmSync` → `POST /api/integration/leads`).
- На staging (`new.uagreen.co`) `GOSPODAR_INTEGRATION_KEY` поки не задано → без нього
  відгуки не підуть (лише email), як і CRM-ліди зараз.

## Підходи (обрано 1)

1. **Явна прив'язка в адмінці сайту** — у вакансії сайту поле «Вакансія в Господарі»
   (список відкритих вакансій із Господаря). Надійно, не залежить від назв. **Обрано:**
   користувач вирівняв списки вакансій і погодив прив'язку кожної вакансії.
2. Автоматично за назвою в Господарі (знайти/створити вакансію). Відкинуто: назви різні
   («Слюсар-зварювальник» ↔ «Зварювальник», «Формувальник» ↔ «Формовщик») → дублікати.
3. Вакансії сайту беруться з Господаря. Відкинуто: у Господарі нема текстів, EN, відділів.

## Як влаштовано

### Господар (репозиторій `D:\Work\Gospodar`, окрема гілка/worktree)

- `GET /api/integration/vacancies` (ключ компанії) → `[{ id, name, status }]`, де
  `name = Title ?? Specialty.Name`; лише відкриті (для списку в адмінці сайту).
- `POST /api/integration/candidates` (ключ компанії), `multipart/form-data`:
  `externalId` (обов'язк.), `fullName`, `phone`, `email?`, `message?`, `vacancyId?`,
  `siteVacancyTitle?`, `cv?` (PDF/DOC/DOCX, ≤ 10 МБ, перевірка magic bytes як у
  `RecruitmentController.UploadResume`).
  - Повтор того ж `externalId` → `200 { candidateId }`, нічого не створює.
    Нова колонка `candidates.external_id` (varchar 64, унікальний індекс
    `(company_id, external_id)` де не null) + міграція.
  - Вакансія: `vacancyId`, якщо така є в компанії (статус не важливий); інакше —
    вакансія «Відгуки з сайту» (знайти за `Title`, або створити зі спеціальністю
    «Без посади», знайти/створити).
  - Пошук наявного кандидата — лише в цьому ендпоінті: телефон порівнюється цифрами
    (`BinotelCallPayload.NormalizePhone` з обох боків, у пам'яті по кандидатах компанії),
    email — без регістру. Перевірку дублів у формах HR (`FindDuplicateError`) не чіпаємо.
  - Знайдено → новий не створюється: до наявної картки додається коментар «Повторний
    відгук з сайту на «{вакансія}» (раніше: «{стара вакансія}»): {повідомлення}», резюме
    у вкладення. Якщо стадія `Rejected` чи `Reserve` → стадія `New` (причину очищає, як
    `SetCandidateStage`) і `VacancyId` = нова вакансія. Активні стадії не чіпаються
    (ні стадія, ні вакансія), щоб не зламати процес — лише коментар.
    Повтор такого відгуку розпізнається за маркером `[site:{externalId}]` у тексті
    коментаря: коментар із цим маркером уже є → `200`, нічого не додається.
  - Новий кандидат: `Stage = New`, `Source = "Сайт uagreen.co"`,
    `Notes = "Вакансія на сайті: {siteVacancyTitle}\n{message}"` (≤ 4000).
  - Коментар від інтеграції: `AuthorId = Guid.Empty`; запит деталей кандидата показує
    автора «Сайт uagreen.co», коли `AuthorId == Guid.Empty`.
  - Відповідь: `201 { candidateId }` — створено; `200 { candidateId }` — повтор або
    дописано до наявного; `400 { error }` — невалідні дані.
- Тести: інтеграційні, за зразком `IntegrationLeadEndpointTests` (новий, повтор,
  дубль-телефон з `Reserve` → `New`, без вакансії → «Відгуки з сайту», чужий ключ → 401/403).

### Сайт (цей репозиторій)

- `Vacancy.GospodarVacancyId` (Guid?, міграція); у `VacancyUpsert`/`VacancyAdminDto`.
- `Application` реалізує `ICrmLinked` через явну реалізацію інтерфейсу на власні
  колонки `GospodarCandidateId`, `GospodarSyncedAt`, `GospodarError`, `GospodarAttempts`,
  `GospodarLastAttemptAt` (міграція) — та сама логіка повторів `CrmSync.Due`.
- `CrmSync.PushAsync(Application)`: multipart на `/api/integration/candidates`,
  `externalId = "site-app-{Id:N}"`, `vacancyId` = `GospodarVacancyId` вакансії сайту,
  резюме з `FileStorage.OpenPrivate`. Помилки — як у лідів (текст у `GospodarError`).
- `CrmSyncWorker`: третій цикл — усі невідправлені відгуки (без 3-денного вікна, як у
  контактів), до 50 за хвилину, з тим самим backoff (20 спроб ≈ 3 доби). Тож і наявні
  рядки, і ті, що накопичились, поки ключа нема, підуть, щойно ключ задано.
- Після успішної відправки резюме видаляється з диска сайту (`DeletePrivate`,
  `CvKey = null`) — воно вже в Господарі. Рядок відгуку лишається (статистика відвідувань
  рахує відгуки по днях).
- Email при відгуку — без змін (йде на скриньку замовлень, резюме не вкладає, тож
  страховкою не є; страховка — список нижче).
- `GET /api/admin/gospodar/vacancies` (роль Hr) → проксі до Господаря для списку.
- Адмінка: у формі вакансії — випадний список «Вакансія в Господарі» (порожнє =
  «Відгуки з сайту»); прибрати колонку «Відгуків» у списку вакансій.
- Розділ «Відгуки на вакансії» стає «Не доставлені в Господар»: лише відгуки без
  `GospodarCandidateId`, з причиною (`GospodarError`), завантаженням резюме і кнопкою
  «Надіслати ще раз» (скидає лічильник спроб, як ручний повтор у замовленнях). Бейдж і
  плитка на дашборді рахують недоставлені. У нормі список порожній. Статуси й нотатки
  відгуку з UI прибрати — відгуком займаються в Господарі.
- Прив'язати 6 активних вакансій staging до вакансій Господаря (після деплою):
  Слюсар-зварювальник → Зварювальник, Слюсар-електронщик → Слюсар-електронщик
  (відкрита, `b63c6149…`), Слюсар металообробки → Слюсар металообробки, Токар → Токар,
  Фрезерувальник → Фрезерувальник, Формувальник → Формовщик.
- Тести: за зразком `GospodarIntegrationTests` (відправка, повтор після помилки, резюме
  видаляється лише після успіху).

## Розгортання

1. Господар: міграція + ендпоінти → деплой на erp.uagreen.co (скіл `gospodar-deploy`),
   лише з окремого OK користувача — це прод ERP.
2. Сайт: деплой на staging; ключ `GOSPODAR_INTEGRATION_KEY` у `.env` сервера задає
   користувач (секрет).
3. Перевірка: відгук на staging → картка в «Новий» у Господарі з резюме.

## Рішення, ухвалені мною (можна виправити)

- Повторний кандидат повертається в «Новий» (і переходить на нову вакансію) лише з
  «Відмова»/«Резерв»; в активних стадіях — тільки коментар.
- Дублі шукаються за цифрами телефону лише для відгуків із сайту; форми HR без змін.
- Недоставлені відгуки лишаються видимі в адмінці сайту (список «Не доставлені в
  Господар») — інакше відгук міг би тихо загубитися.
- Наявні відгуки в базі сайту (на staging — 1) теж підуть у Господар.
- Резюме видаляється з сайту після успішної передачі.
- Список у адмінці — лише відкриті вакансії Господаря.
- Без сповіщень у Господарі.

## Лишаю будівельнику

Імена класів/файлів, точна форма DTO, тексти помилок, розмітка випадного списку.
